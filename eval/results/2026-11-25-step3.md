# Authoring eval: after `13` step 3's first fixes

Re-runs of the [baseline](README.md) after the fixes its failures pointed at.
Same tasks, models and settings; norman 0.4.0 with the changes below.

## What changed

- **The reference** says a site is written literally in the `ask` (with an
  example of sharing a context between two asks), that a scripted `reply` is
  JSON, and that types and per-file script names are defined once.
- **The parser:** a non-literal site gets a message that says what to do
  instead. The definition it was in no longer comes back as "unbound name"
  at every use.
- **The checker:**
  - A second `datatype` or `record` of a name is rejected (it used to replace
    the first silently).
  - A test `under` a script that doesn't exist is rejected before anything
    runs.
  - A file defines each script name once.
- **A checker bug the re-run found** (below): an `Ord` on a field's type
  was defaulted to Num.

## The numbers

There were two re-runs:

- **The first** had a wrong version of the script rule: script names were
  global and defined once. The hidden tests `use` the solution and then
  define their own scripts. A solution whose tests used the same script
  names (`approves`, `yes`, `tie`) was therefore rejected before the hidden
  tests ran, in 17 trials, 11 of them in Sonnet `ref+examples`. Its pass
  rates are not comparable, and it isn't kept here. Its counts of the
  targeted causes below still are.
- **The second**, on the corrected rule, is the one in the table. The Haiku
  runs stopped when the account ran out of API credit, after 50 and 47 of
  their 60 trials. Tier E is barely covered and tier F not at all.

| model, condition | trials | check@1 | pass@1 | pass@R | baseline pass@1 |
|---|---|---|---|---|---|
| Sonnet 5.5, `ref` | 60 | 98% | 98% | 100% | 95% |
| Sonnet 5.5, `ref+examples` | 60 | 92% | 92% | 100% | 100% |
| Haiku 5.5, `ref` | 50 (stopped) | 98% | 98% | 100% | 93% |
| Haiku 5.5, `ref+examples` | 47 (stopped) | 94% | 98% | 100% | 95% |

With three trials per task, a few points either way is noise. **The per-cause
counts are the measure that matters**, and they cover all 457 first programs
written after the fixes (both re-runs):

| baseline cause | before (240 trials) | after (457 trials) |
|---|---|---|
| a site passed as an argument | 5 (of 12 `E01` trials) | **0** (of 20 `E01` trials) |
| a scripted reply written as bare text | 1 | **0** |
| a test under a script that doesn't exist | 1 | **0** |
| redefining the interface | 4 | 5, now all caught, including records and datatypes |

So the site, `reply` and script fixes did what they were for. Redefinition is
a habit of Haiku's that no message prevents, but each one is now caught at
the definition instead of surfacing as an "unknown constructor" in the
hidden tests.

## A checker bug the re-run found

Sonnet's `A01` failed its first round in 6 trials across the re-runs (none in
the baseline): "This test is ill-typed: expected Text, but found Num". The
model compared words with `<` and `>`, inside a helper that reads a pair's
`fst`:

```
(define first-below? (p w) (< (. p fst) w))
(first-below? (Pair [fst "a"] [snd 1]) "b")   ; was rejected
```

`settle` decided which type variables the definition's type mentions before
resolving the field. Resolving `(. p fst)` binds the field's type to `Pair`'s
parameter, a variable that wasn't in the set, so the `Ord` on it looked
ambiguous and was defaulted to Num. That's against design/12 §3's own
rule: a constraint the type mentions stays generic. The fix follows the set
through the substitution at each pass. With it, all six rejected programs
pass their own tests and the hidden ones. `tests/check.rs` has the case.

The baseline never met this only because Sonnet happened to compare with
`=`. It is a real bug, and any program that orders record fields in a helper
hit it.
